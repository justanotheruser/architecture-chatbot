## Как читать эту вики

- Это не “идеальная” документация, а рабочая база знаний с артефактами реальной разработки.
- Некоторые страницы дублируют фрагменты информации с разными акцентами.
- Есть устаревшие куски: мы их не прячем, а помечаем, потому что это полезно для онбординга.
- Разделы про целевую архитектуру и фактическую реализацию могут расходиться.
- Для большинства ответов по архитектуре нужно сопоставлять 2-4 страницы, а не одну.

## Быстрый вход в проект

- Продукт: Telegram-бот для интерактивных историй и практики языка.
- Основной runtime: `bot_server/lexi`.
- Текущий стек исполнения: aiogram + FastAPI + PostgreSQL + Redis + OpenAI.
- Планируемые/частично задокументированные элементы: Celery-воркеры, генерация обложки, event stream.
- Основной источник правды по коду: Python-модули в `bot_server/lexi`.
- Основной источник правды по продуктовой цели: `PRD.md`.

## Текущая архитектурная картинка (коротко)

- Обновления из Telegram приходят либо через webhook endpoint, либо через polling режим.
- В `Dispatcher` собираются middleware, роутеры и сервисы.
- Пользовательская информация хранится в PostgreSQL (сейчас главным образом `users`).
- Сессионная история сказки и кэш словаря лежат в Redis.
- Генерация текста и модерация идут через OpenAI API.
- Story session живет в Redis-ключах с префиксом `story_session`.

## Что важно помнить новым участникам

- В репозитории есть “следы прошлого” с неймингом `app.*` в тестах и старых заметках.
- Часть PRD-функций еще не реализована в коде (квизы/обложка/полная аналитика прогресса).
- В `diagrams/to_be` отражено то, что обсуждалось как next phase, а не текущий факт.
- Разделы с пометкой “гипотеза” нельзя напрямую превращать в тикеты без проверки.
- Валидация пользовательского ввода завязана на external moderation API и фича-флаг.

## Что специально распределено между страницами

- Детали Redis-ключей и TTL описаны в `data-models` и частично в `workflows`.
- Расхождения PRD vs код описаны в `system-overview`, но примеры тестовых артефактов в `known-issues`.
- Нюансы around story language preference описаны в `components` и `strategy-and-rnd`.
- Ограничения парсинга LLM-ответов разбросаны между `workflows`, `known-issues`, `strategy-and-rnd`.
- Причины, почему Celery есть в зависимостях, но не в runtime, описаны в двух местах с разной формулировкой.

## Мини-карта директорий

- `bot_server/lexi`: приложение и бизнес-логика.
- `bot_server/alembic`: миграции, сейчас три ревизии для таблицы `users`.
- `bot_server/assets/messages`: локализация (FTL).
- `deployment`: docker compose для app/db/redis.
- `diagrams/as_is`: документация текущего контейнерного уровня.
- `diagrams/to_be`: целевая (планируемая) архитектура.
- `story_teller`: историческая заметка по FSM-рефакторингу с устаревшими путями.

## Контрольные вопросы перед изменениями

- Эта функция уже есть в коде или только в PRD/диаграммах?
- Изменение трогает только runtime бота или еще devcontainer/deployment?
- Нужно ли обновлять миграции и DTO одновременно?
- Будет ли изменение ломать совместимость с текущими Redis-сессиями?
- Нужен ли fallback, если OpenAI API недоступен?
- Достаточно ли тестов из `bot_server/tests` для проверки изменения?

## Часто задаваемые внутренние вопросы (быстрые ответы)

### “Где смотреть текущий production-like поток?”

- В первую очередь `wiki/workflows.md`.
- Затем проверить `lexi/telegram/handlers/story_creation.py` и `story_dialog.py`.

### “Почему в PRD есть то, чего нет в коде?”

- PRD фиксирует цель и направление, а runtime отражает текущую стадию.
- Расхождения отмечены в `wiki/system-overview.md` и `wiki/known-issues.md`.

### “Можно ли полагаться на старые docs из папки story_teller?”

- Только как исторический контекст.
- Для текущих путей модулей смотреть namespace `lexi/*`.

### “Почему Celery упоминается так часто?”

- Оно есть в зависимостях и целевой архитектуре.
- Но фактический runtime пока без активного worker-контура.

### “Где точка входа для новых изменений?”

- Для UX: handlers.
- Для бизнес-логики: services.
- Для схем: models + alembic.

## Командный словарь терминов

- **Story Session**: состояние активной истории в Redis.
- **Story Bit**: один фрагмент истории с вариантами выбора.
- **Choice Drift**: ситуация, когда choices не соответствуют ожиданиям parser-а.
- **PRD Drift**: расхождение между PRD и фактической реализацией.
- **As-Is**: то, что работает в коде сейчас.
- **To-Be**: целевая архитектура или план.
- **Flow Break**: пользователь дошел до шага, но не может продолжить без ошибки.
- **Soft Legacy**: старые артефакты, которые еще не удалены, но мешают контексту.

## Мини-гайд по обновлению вики

1. При изменении runtime-flow обновить:
   - `workflows`
   - `components`
   - при необходимости `known-issues`
2. При изменении схем:
   - `data-models`
   - `historical-evolution`
3. При принятии нового компромисса:
   - `strategy-and-rnd`
   - `internal-discussions`
4. При закрытии техдолга:
   - отметить статус в `known-issues`
5. Для новых RAG-кейсов:
   - добавить вопросы в `questions`

## Сигналы, что вики устаревает

- В коде появились новые handlers/services, а в `components` их нет.
- В миграциях есть новые поля, а в `data-models` их не описали.
- Поменялся путь запуска, но `system-overview` еще старый.
- В known issues осталось “open”, хотя фикс уже влит.
- Вопросы из `questions` больше не отражают реальные ambiguity зоны.
