# Internal Discussions (рабочие заметки)

> Этот файл намеренно “шумный”: краткие синопсисы разговоров, спорные идеи, не до конца проверенные гипотезы.

## Канал: архитектура

- “Мы рассматривали отдельный сервис Story Teller, но пока оставили inline в боте.”
- “Если пойдем в worker модель, то нужно будет заново определить ownership retries.”
- “Не до конца ясно, стоит ли оставлять Redis единственным местом story state.”
- “Есть ощущение, что на scale parser ошибок станет заметно больше.”
- “Нужен компромисс: не перегрузить MVP, но убрать самые хрупкие контракты.”

## Канал: продукт

- “Квизы есть в PRD, но в реальности лучше сначала стабилизировать базовый сюжет.”
- “Без обложки в конце история кажется незавершенной, retention может проседать.”
- “Словарь работает, но качество выбора слов пока спорное.”
- “Мы чуть упростили возрастной тон промптов, но еще не мерили эффект.”
- “Стоит ли выводить ‘сложность истории’ как отдельную настройку?”

## Канал: качество/тесты

- “Тесты после неймспейс-рефакторинга выглядят как техдолг, который все откладывают.”
- “Нужно определить минимальный набор smoke тестов, который реально запускается.”
- “Мы не покрываем parser edge cases так, как надо.”
- “Хотелось бы golden set для LLM outputs.”

## Канал: инфраструктура

- “Celery в зависимостях сейчас больше как след из старого плана.”
- “Если все же идти в очередь, возможно RabbitMQ не обязателен, можно начать проще.”
- “В документации devcontainer упоминания про broker есть, но runtime без этого живет.”

## Сырые тезисы из ретро

- “Переформулировали цель: сначала ‘интересная история’, потом ‘педагогическая точность’.”
- “Расхождения PRD и кода неизбежны, главное — помечать, где факт, а где план.”
- “В некоторых местах мы переоценили скорость внедрения асинхронного контура.”
- “Проблема не в том, что нет Celery, а в том, что нет единого решения по orchestration.”
- “Нужно меньше скрытых side-effects в middleware.”

## Обсуждения по данным

- “Хотим сохранять финальные истории, но еще спорим про формат.”
- “Если хранить все шаги, быстро вырастут объемы и вопросы по privacy.”
- “Может хватит summary + метаданных вместо полного текста?”
- “Словарь в Redis хорош для скорости, но не дает долгосрочного прогресса ученика.”

## Что может сломаться (цитаты)

- “Это может ломаться, если модель перестанет отдавать choices нумерованным списком.”
- “Не полностью протестировано на длинных историях и редких языках.”
- “Есть риск, что в callback редактировании сообщения словим race.”
- “Если moderation API недоступен, пользователь получает отказ и может уйти.”

## Частично устаревшие мнения (сохраняем для контекста)

- “Будем сразу пушить всё в отдельный stream processor.” (пока не реализовано)
- “Сделаем fuzzy language input основным каналом выбора.” (сейчас основной path через кнопки)
- “Квизы добавим буквально в следующем спринте.” (переносилось несколько раз)

## Решения, которые обсуждались, но не приняты окончательно

- strict schema validation для каждого LLM response;
- fallback LLM provider;
- хранение `story_text` в SQL на каждом шаге;
- вынесение vocab helper в отдельный микросервис.

## Точки согласия (пока)

- Сейчас приоритет — стабильный core flow.
- Техдолг по тестам больше нельзя игнорировать.
- Нужно явно развести “as-is” и “to-be” в техдоках.
- Нужен owner для story completion reward (обложка/трофей).

## Вопросы, которые регулярно всплывают

- Должны ли мы persist-ить каждую реплику истории?
- Нужно ли версионировать формат `StorySession`?
- Что важнее в следующем спринте: quiz или качество parser-а?
- Как корректно мерить “педагогическую ценность” story output?
- Нужно ли включать user feedback прямо в Telegram flow?

## Неочевидные противоречия в обсуждениях

- Часть команды хочет “минимум инфраструктуры”, часть — “сразу надежный async контур”.
- Одни считают, что strict moderation слишком жесткая, другие — что это обязательный safety baseline.
- Есть разные мнения, где проводить границу между продуктовой логикой и prompt engineering.

## Внутренние предположения (не все подтверждены)

- “Если добавить quiz, пользователи будут дольше оставаться в диалоге.”
- “Если хранить финальные истории, родители чаще возвращаются.”
- “Если сделать обложку асинхронной, лучше не ждать её в текущем диалоге.”
- “Если оставить всё inline, расходы на отладку со временем станут выше.”

## Риски, о которых говорили, но не формализовали

- vendor lock-in на одном LLM провайдере;
- лимиты Telegram callback UX при длинных кнопках;
- language-specific edge cases для parser-а;
- постепенный рост “полудокументированных” решений.

## Протокол “не до конца протестировано”

- Story flow на длинных контекстах.
- Поведение в редких языках интерфейса.
- Нагрузочные сценарии массовых параллельных сессий.
- Качество vocabulary определений при шумном контексте.

## Рабочие правила, появившиеся из дискуссий

- Если спор о фиче длится > 2 спринтов, фиксируем ADR или explicit defer.
- Если расхождение PRD/кода влияет на планирование, добавляем заметку в known issues.
- Если поменяли namespace/структуру, обновляем тесты в том же цикле.
- Если добавили новую зависимость, проверяем фактическое использование.

## Что команда считает “сделано”

- User can start story flow.
- User can continue story with choices.
- User can get vocabulary hints.
- Бот не ломается на базовом happy path.

## Что команда НЕ считает “сделано”

- Тесты покрывают все критические edge cases.
- Продуктовая аналитика готова.
- Финальная reward-механика полностью закрыта.
- Долг по докам и legacy следам закрыт.

## Финальная ремарка

- Эти заметки не заменяют ADR, но фиксируют контекст, который обычно теряется.
- Любая спорная тема из этого файла должна иметь follow-up владельца.
- Если пункт повторяется 2+ спринта подряд, он переходит в formal decision log.
- Важно не только “что решили”, но и “почему не решили сейчас”.
- Для новых участников файл полезен как карта реальных дискуссий, а не polished narrative.
- Неочевидные риски лучше сохранять здесь, чем терять между митингами.
- Раз в месяц проводим cleanup: закрытые темы архивируем, активные переносим в roadmap.
- В случае конфликта с кодом приоритет у фактической реализации, но с пометкой о дрейфе.
- Если решение изменилось, старую позицию не удаляем, а отмечаем как superseded.
