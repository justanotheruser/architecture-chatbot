# Historical Evolution

## Кратко

Проект развивался волнами:  
идея -> MVP с фокусом на core UX -> локальная стабилизация -> накопленный техдолг -> новая попытка структурировать решения.

## Этап 1: Продуктовая постановка

- Появился PRD со сценарием “история + языковая практика”.
- Сразу закладывались амбициозные элементы:
  - quiz;
  - image reward;
  - async jobs и worker architecture;
  - расширенная SQL модель.
- На практике команда решила сначала собрать core narrative loop.

## Этап 2: Сборка раннего runtime

- Собрали бота на aiogram.
- Добавили FastAPI как hosting/webhook слой.
- Подключили Postgres и Redis.
- Выделили первичные сервисы для user/story logic.

## Этап 3: FSM-рефакторинг story setup

- Story creation вынесен в отдельный FSM flow.
- Улучшилась управляемость шагов (language/protagonist/setting).
- Добавилась moderation проверка пользовательского текста.
- В истории проекта остались документы с путями `app/...`.

## Этап 4: Локализация и UX-полировка

- Разросся набор FTL-файлов.
- Добавлены команды меню для смены UI language и story language.
- Пользовательский профиль стал хранить предпочтение языка истории.

## Этап 5: Промежуточная стабилизация

- Появились health endpoints (liveness/readiness).
- Story session lifecycle закрепился в Redis.
- В vocabulary flow появился кэш с TTL.

## Этап 6: Осознание разрыва “доки vs код”

- PRD и to-be диаграммы отражали более сложную систему.
- Runtime остался компактным и рабочим, но не полностью совпадающим с планами.
- В тестах и некоторых заметках проявился legacy namespace (`app.*`).

## Миграционная линия по пользователю

- `init` миграция создала базовую таблицу users.
- добавили поле `last_story_language_code`.
- переименовали его в `story_language_code`.
- тестовые артефакты частично остались на старом имени.

## Что менялось без полного следа в документации

- Логика language selection в story flow стала преимущественно callback-based.
- Подходы к prompt tuning регулярно менялись без формального changelog.
- Некоторые компромиссы (например, parser эвристики) закрепились как “временно постоянные”.

## Что так и не довели до прод-уровня

- Квизовый поток в пользовательском сценарии.
- Генерация обложки в финале истории.
- Event stream pipeline для аналитики.
- Полноценный слой хранения итоговых историй.

## Версии архитектурного нарратива

- **Narrative A (PRD):** широкая распределенная система с async worker flow.
- **Narrative B (runtime):** компактный monolithic bot runtime с внешним LLM.
- **Narrative C (командные заметки):** “сначала стабильность core, потом расщепление”.

## Выводы из эволюции

- Команда успешно довела MVP сценарий до рабочего состояния.
- Быстрые итерации дали ценность, но создали документный и тестовый долг.
- Следующий качественный скачок потребует не только кода, но и синхронизации решений/доков.

## Исторические lessons learned

- “Не все, что в PRD, должно попасть в первый production runtime.”
- “Лучше явный backlog техдолга, чем молчаливый дрейф.”
- “Если меняется namespace, тесты должны мигрировать сразу, а не потом.”
- “Нужно иметь один понятный артефакт ‘что сейчас в проде’.”

## Возможная следующая эволюция (гипотезы)

- Вынести generation в job orchestration (не обязательно сразу Celery).
- Добавить structured contract для LLM outputs.
- Сохранение финальных историй и базовой аналитики в SQL.
- Свести docs к двухслойной модели: as-is + roadmap.

## Расширенный timeline (черновик)

### T0 — pre-implementation

- сформулирован образовательный сценарий;
- выбрана Telegram как первичная платформа;
- записаны идеи по quiz и image reward.

### T1 — first runtime baseline

- добавлен базовый запуск и конфигурация;
- подняты postgres/redis зависимости;
- создан минимальный user persistence flow.

### T2 — dialog-driven MVP

- story creation переведен в FSM;
- настроены callback-цепочки;
- добавлена базовая модерация входных данных.

### T3 — quality tuning

- prompt шаблоны вынесены в отдельный модуль;
- добавлен vocabulary helper;
- кэширование словаря в Redis.

### T4 — stabilization phase

- health endpoints;
- частичное расширение i18n;
- миграции story language поля.

### T5 — drift recognition

- осознание разрыва между PRD и runtime;
- фиксация known issues;
- обсуждения про worker strategy.

## Изменения, которые “почти случились”

- пилот с очередями задач (остался на уровне обсуждений/диаграмм);
- ранний набросок event stream процессора;
- более глубокая модель user progress.

## Версии команды о причинах техдолга

- версия A: “слишком быстрые продуктовые итерации”;
- версия B: “недостаток ownership на инфраструктурный слой”;
- версия C: “часть инициатив зависла между R&D и продуктом”.

## Эволюция языка документации

- ранние документы были ближе к aspirational описанию;
- затем появились более практичные заметки;
- текущая вики объединяет обе перспективы.

## Контрольные точки, которые стоит повторять

- сверка диаграмм и runtime раз в релиз;
- сверка тестов и namespace после крупных рефакторингов;
- фиксация trade-offs в отдельном ADR-потоке.

## Исторические “повороты”

- Поворот 1: от “все сразу” к “core flow first”.
- Поворот 2: от монолитного handler logic к service split.
- Поворот 3: от веры в быструю async-оркестрацию к поэтапной стратегии.

## Неформальные артефакты, важные для контекста

- старые заметки с `app/...` путями;
- to-be диаграммы с компонентами, которых нет в runtime;
- зависимости, включенные заранее под будущую архитектуру.

## Возможные next milestones

- M1: привести тесты к текущему namespace.
- M2: стабилизировать parser и structured output.
- M3: решить вопрос persistence финальных историй.
- M4: внедрить понятную стратегию async jobs.
