# Design Decisions, R&D Notes, Discussions, Historical Evolution

## 5) Design Decisions

### D-01: Выбор aiogram + FastAPI в одном runtime

**Почему выбрали:**

- быстрое MVP без отдельного gateway;
- webhook и polling в одном кодовом базисе;
- понятная команда поддержки.

**Trade-offs:**

- runtime смешивает HTTP слой и бот-логику;
- сложнее изолировать нагрузку по компонентам.

**Что отвергли:**

- отдельный Telegram gateway service + internal RPC.

---

### D-02: Redis как state store для story sessions

**Почему выбрали:**

- нужен быстрый mutable state между шагами сюжета;
- минимальный overhead на старте.

**Trade-offs:**

- session state неперсистентный как продуктовый артефакт;
- schema migration для Redis-объектов неформализована.

**Что отвергли:**

- сразу сохранять каждую реплику в SQL.

---

### D-03: OpenAI Moderation для пользовательских текстов

**Почему выбрали:**

- безопасный baseline для детской аудитории;
- простой integration path.

**Trade-offs:**

- внешний API становится критической зависимостью для UX;
- conservative reject при ошибке API.

**Что отвергли:**

- локальная фильтрация regex-only без внешней moderation.

---

### D-04: Простая эвристика для key words

**Почему выбрали:**

- скорость реализации MVP;
- низкая когнитивная сложность кода.

**Trade-offs:**

- качество выбора слов нестабильно;
- повторения возможны.

**Что отвергли:**

- сложный ranking на корпусной статистике с первого релиза.

---

### D-05: Хранить prompts в отдельном модуле

**Почему выбрали:**

- проще итерации на prompt engineering;
- уменьшение шума в handlers/services.

**Trade-offs:**

- prompt drift может расходиться с бизнес-требованиями;
- сложно version-control “эффект” конкретного prompt.

**Что отвергли:**

- инлайн prompts в каждом service method.

## 5.1) Отмеченные компромиссы, которые живут до сих пор

- Мы держим “быстрое” решение с parser regex, пока не появится явный schema parser.
- Мы оставили Celery в зависимости и документации, хотя runtime еще не переведен на worker model.
- Мы сознательно не блокировали релиз из-за неполного слоя аналитики.

## 5.2) Rejected alternatives (кратко)

- Полностью event-driven архитектура в первой итерации.
- Отдельный микросервис image generation до стабилизации story UX.
- Сложная пользовательская модель с десятками полей до появления практической потребности.

## 6) Experiments / R&D Notes

### Что сработало

- Эксперимент с FSM для story creation (разделение шагами) улучшил предсказуемость flow.
- Перенос локализации на Fluent-файлы упростил правки сообщений.
- Кэш словаря в Redis заметно сократил повторные запросы к LLM в рамках одной сессии.
- Разделение сервисов на `StoryCreator` и `StoryTeller` оказалось полезным для читаемости.

### Что не сработало (или не доведено)

- Идея с quiz every N turns осталась на уровне prompt helper, без runtime integration.
- Концепт image generation в конце истории не дошел до production цепочки.
- Legacy тесты после рефакторинга namespace не были полностью мигрированы.
- Попытка держать PRD и код в полном синке вручную оказалась нереалистичной.

### Гипотезы для следующего цикла

- Добавление structured output schema для LLM снизит ошибки parser.
- Отдельный worker для story generation улучшит SLA и retry-поведение.
- Persist финальных историй в SQL повысит ценность продукта для родителей/аналитики.
- Нормализация словаря (лемматизация) улучшит educational quality подсказок.

### Micro-notes (внутренние)

- [R1] Иногда LLM возвращает choices на “неправильном” языке после длинного контекста.
- [R2] Character growth вставки могут выглядеть оторванными от основной сцены.
- [R3] Порог turn-count как критерий финала дает неровную длительность историй.
- [R4] В некоторых языках локали слова для кнопок длинные, интерфейс выглядит перегруженным.
- [R5] Смешение HTML-тегов в story output требует аккуратной валидации.

- “Не до конца ясно, где лучше хранить финальные истории: SQL или object storage + индекс.”
- “Надо решить, есть ли смысл держать Celery зависимость, если в текущем runtime не используем.”
- “Технически можно продолжать без воркеров, но дебаг latency будет тяжелее.”
- “Есть шанс, что при масштабировании callback editing начнет давать edge-case ошибки.”
- “Пока оставим, но зафиксируем как known risk.”

### Обсуждения, требующие follow-up

- Нужна ли миграция на строгий event schema для story progress?
- Делаем ли отдельный сервис аналитики или сначала пишем в Postgres напрямую?
- Как тестировать multi-language quality системно, а не вручную?
- Делаем ли user-facing экспорт финальной истории (pdf/image/text)?

## 9) Historical Evolution

### Фаза 0: Идея и PRD-рамка

- Появился продуктовый сценарий “язык через приключение”.
- Были заложены амбициозные компоненты: quiz, image reward, worker-driven async.
- Схема БД в PRD предполагала больше таблиц, чем стартовый runtime.

### Фаза 1: MVP runtime

- Сфокусировались на core flow:
  - story setup;
  - story continuation;
  - vocabulary helper.
- Подняли FastAPI + aiogram + Redis + Postgres.
- Схему SQL сократили до `users`.

### Фаза 2: Улучшение UX и state

- Story creation перевели на FSM-подход.
- Добавили language preference для story language.
- Уточнили миграции поля story language (rename sequence).

### Фаза 3: Частичная стабилизация

- Расширили набор локалей.
- Привели структуру сервисов к более явному виду.
- Добавили health readiness/liveness.

### Что “застряло” между фазами

- Quiz flow.
- Story cover generation.
- Event stream для аналитики.
- Полное покрытие актуальными тестами.

### Почему так произошло (практически)

- Команда выбрала скорость поставки core value.
- Технический долг принимался осознанно.
- Документация и код обновлялись не всегда синхронно.
- Некоторым идеям не хватило чёткого owner-а.

## Сводка по разделам 5/6/8/9

- Мы сознательно выбрали быстрый продуктовый путь с мягкой архитектурой.
- Несколько планов остались в “следующей итерации”, но их артефакты видны уже сейчас.
- Текущее состояние рабочее, но для масштабирования нужны более строгие контракты.
